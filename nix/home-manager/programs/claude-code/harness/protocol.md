# 開発プロトコル（正典）

拓也の個人開発体制。どのリポでも同じ。リポ固有のことはリポの `.harness/protocol.md`（差分）と
`.claude/settings.json`（コマンド）と `.claude/rules/`（ドメイン）に置き、ここには書かない。
矛盾したら、**判断はこのファイル、コマンドと境界はリポ側**が勝つ。

出自: zj-plan（2026-08, zellij 5 ペイン）→ frank の CODEX_DEVELOPMENT.md（2026-09）→ 本ファイル（2026-11）。
Anthropic「Solving code review at Anthropic」と Claude Code 公式ベストプラクティスの考え方を取り込んでいる。

## 0. 二層の原則

| 層 | 置き場所 | 中身 |
|---|---|---|
| 作法（全リポ共通） | `~/.claude/harness/`（dotfiles）, `~/.claude/skills/`, `~/.claude/agents/` | 役割、発注書、レビュー規律、裁定、計測、予算 |
| リポ固有 | `<repo>/.claude/settings.json`, `.claude/rules/`, `.harness/protocol.md`, `AGENTS.md` | 検証コマンド、高リスクの具体例、承認境界、他人・他ツール向けの宣言 |

「必ず守る」ルールは文章にせず **Stop hook / deny / `/goal`** に置く。Claude はガイドラインを読み飛ばせるが、ツールは飛ばさない。

## 1. 役割（モデル非依存）

| 役割 | 仕事 | 既定の担当 | 切り替える条件 |
|---|---|---|---|
| **主担当** | 拓也の窓口。発注・優先度・設計判断・統合・裁定。長文の成果物は自分で書かない | Claude デスクトップ（または Codex Astra をリポが指定していればそれ） | — |
| **実装** | 発注書の範囲で実装し、対象検証して証跡を返す | Claude builder（`/impl`） | Claude が使えない／適性上必要なら Codex 実装担当。途中での重複実装はしない |
| **調査** | 原因不明の限定調査。根拠に file:line と SHA | Claude サブエージェント（Explore） | 既知の修正や 1 値の確認では起動しない |
| **evaluator** | 実際に動かして AC を採点 | `evaluator` サブエージェント | — |
| **evidence-reviewer** | 差分 × AC を表で照合 | `evidence-reviewer` サブエージェント | — |
| **独立レビュー** | 別ベンダーの目。観点別・read-only・P0/P1/P2 | Codex Sol（`/sol-review`） | 難しい認可・状態機械・migration・外部書込みは主担当も見る |
| **裁定（衝突時）** | P1 級の見解対立・高リスクの最終判断 | Claude Opus（必要時のみ） | 第三の全体レビューを常設しない |
| **小修正** | 所有ファイルと期待挙動が明確な修正・fixture・文書同期 | 主担当、または Codex Terra/Luna | 委譲が単独処理より有益な具体的な仕事だけ |

通常は **実装 1 名 ＋ 必要時の独立レビュー**。実装の並列は、契約・migration・所有ファイルが独立する **最大 2〜3 件**。同じ Docker/DB/ポートを使う試験は並列にしない。

## 2. 発注書（契約）— 実装前に書く

`/slice` が `.harness/requests/<slug>.md` に書く。**実装中に AC を書き換えない**。変えたくなったら主担当が拓也に上げて止まる。

必須項目: 目的 / スコープ（触る・触らない）/ **機械判定できる AC と検証方法** / 入力資料（仕様・rules・既決事項）/ 実装者裁量と要判断 / リスク階層 / 証跡の返却先。
小修正は 目的・AC・検証 の 3 行でよい。PR は行数ではなく **業務上意味のある機能単位**。

担当への依頼はこの発注書の担当部分を切り出す。同じ仕様を別ブリーフに書き直さない。モデルが変わっても完成条件は変えない。

## 3. 無人実行の予算

print モード・定期タスク・バックグラウンドで走らせるときは、**ターン数・時間・API 換算額の上限**を必ず指定する。

| 単位 | 目安 |
|---|---|
| 小修正 | `--max-turns 50`、900 秒、API 換算 5 ドル |
| 接続/E2E を含む単位 | `--max-turns 90`、900 秒、5 ドル。残作業・所有ファイル・証跡を限定できるなら 150 ターン・1800 秒・8 ドルまで |

- 125 ターン前後で実装を区切り、残りを検証と結果保存に残す
- **上限到達を成功と読み替えない**。exit 0 だけで完了扱いにせず、最終 result の success と証跡を見る
- 既に完了した範囲を再実装しない。自動で別担当へ同じ実装を再発注しない
- ターン数・ツール呼出し回数・経過時間は別々に記録する（集計 turn 数は厳密な上限ではない）

## 4. レビューの規律

- レビュー対象は **ファイル化された成果物** のみ。書きかけ・口頭案は依頼しない
- 指摘は **P0（致命）/ P1（重要）/ P2（改善）**。実装レビューは **file:line** と再現条件を添える
- 判定基準は「コードとして変か」ではなく「**AC を満たすか**」。AC が不十分ならそれを P1 で指摘
- 優先して見る: 既存ロジックの消失・回帰、認可、境界値、エラーパス、競合、再送、部分失敗。**style は見ない**
- 未検証を欠陥と断定しない。「通過 / 未検証 / 残るリスク」を分けて返す
- **2 パス上限**。1 巡目は発見（xhigh）、2 巡目は修正差分のみ（medium）。終了条件は「新規 P0/P1 ゼロ」。検証パスで新規 P1 が出たらラウンドを増やさず拓也へ
- 同一ソースで成功した試験・全体レビューを繰り返さない。指摘ゼロを目標に周辺改善を探し続けない
- 独立レビューの発注は主担当が持つ。実装担当がレビュアーを再起動しない

## 5. 裁定（主担当の仕事）

レビュアーの指摘を**そのまま採用しない**。`/adjudicate` で次に振り分け、`.harness/review-log.jsonl` に 1 指摘 1 行で残す。

| 振り分け | 条件 |
|---|---|
| **fix** | P0。AC 違反。2 つ以上のレビュアー／観点が独立に同じ箇所を指摘した P1 |
| **issue** | P1 のうち発注書の AC 外。P2 全部。根拠と追跡先（Issue）を残す |
| **reject** | 意図的な設計、AC と矛盾、根拠なし、slice と無関係な既存コード由来（`pre-existing`） |

タグ: `fixed` / `wrong` / `intended` / `minor`。P1 級の見解対立・高リスク裁定は Opus（または拓也）へ。

## 6. リスク階層

リスクは**作者ではなく変更内容**で決める。迷ったら 1 段上げる。「高」の具体例はリポの `.harness/protocol.md` に書く。

| リスク | 一般的な例 | 独立レビュー | evaluator | 拓也 |
|---|---|---|---|---|
| 低 | docs、テスト追加、lint、依存バージョン、フラグ付き追加 | medium 1 観点 | 任意 | 見ない |
| 中 | 通常の機能変更 | xhigh 3 観点 | 必須 | 裁定結果を読む |
| 高 | 認証・認可、個人情報、外部送信・外部書込み、秘密情報、DB スキーマ、CI/CD、公開 API の破壊的変更 | xhigh 3 観点 | 必須 | マージ前に必ず見る |

## 7. 証跡

成果の報告は要約ではなく証跡で行う: **対象 SHA・実行コマンド・終了状態・要点と件数・ログの場所**。
「テストが通った」だけは不可。CI は指定 SHA と必要チェックの全成功を確認する。古い観測は後のソース変更の合格証拠にならない。
検収とレビューは **同じ SHA と証跡** を使う。

## 8. 引き継ぎ

機能の区切りで `progress.md` を更新してから終わる（Task / Outputs / Completed / Decisions / Open issues / Next action / Ask）。
履歴やログ全文を転送せず、判断・未確認・SHA・証跡・次の一手だけを渡す。新しいセッションはまず `progress.md` を読み、Outputs を開いて確かめてから進む。

## 9. 計測と見直し（月 1）

- `review-log.jsonl` を reviewer × 観点で集計。`wrong` 率 40% 超の観点は依頼文を直すか Claude 側に寄せる。0 件の観点は外す
- 本番で踏んだバグの PR を `.harness/evals/` に貯め、レビュアーがそれを拾えるか試す
- 所要時間・修正往復・重大欠陥の見逃し・リバートを単位ごとに記録。使用率の削減だけで合否を決めない
- モデルが更新されたら部品を 1 つ外して同じ slice を回し、結果が変わらなければ外したまま

## 10. 止まる条件（エスカレーション）

P1 級の見解対立 / 設計判断そのもの / AC を変えたくなった / 高リスク階層 / 2 パス目で新規 P1 / 承認境界（本番投稿・migration・release guard）に触れる。
止まるときは `progress.md` の Ask に「何を決めてほしいか」を 3 行以内で書く。
